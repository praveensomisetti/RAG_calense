# ChemRAG: Repository Guide

**What this is:** a walkthrough of every folder and file in the repo. For each one it covers **what it contains, what it does and why it exists**, written so you can understand the system and then explain it to an interview panel. It describes behaviour and design, not individual lines of code.

**How to read it:**
- **§1–§3:** the big picture and a map of the repo.
- **§4–§10:** one section per folder, each file in the same format.
- **§11:** follows one real question through the files. This is the best section to rehearse before a demo.
- **§12–§15:** design Q&A, a demo-call script, limitations and a glossary.

---

## 1. The 60-second summary

The California Department of Public Health publishes a dataset of cosmetic products that contain chemicals linked to cancer or reproductive harm: 114,635 rows covering products, companies, brands, categories, chemicals, CAS numbers and dates. The assignment asks for a **multi-agent assistant** that answers plain-English questions about this data with:

- a natural-language answer,
- **evidence**: the exact source rows (CDPHId, CSFId, ChemicalId),
- a **query plan** showing how the answer was produced,
- **confidence and warnings**.

The core design rule:

> **The LLM understands the question and writes the sentences. It never produces a number.**
> Every count comes from a logged SQL query against a cleaned database, every claim cites source rows, and the LLM's text is fact-checked before the user sees it.

**Main technology choices**

| Concern | Choice | One-line reason |
|---|---|---|
| Facts and counting | **DuckDB** (embedded SQL database) | Exact, fast and citable; a single file with no server |
| Matching messy names | **gte-large** embeddings in **Chroma** (embedded vector DB), plus **rapidfuzz** spelling match | Finds "acetaldehide" → Acetaldehyde, or "vitamin A palmitate" → Retinyl palmitate |
| Agent workflow | **LangGraph** | A visible graph of steps, a pause-and-ask feature for clarification, and loops for multi-part questions |
| Language understanding | **OpenAI** (default `gpt-5-mini`) behind a one-method interface | Small and cheap. The system still works with no LLM at all |
| Contracts between steps | **Pydantic** models | Every message between agents is typed and validated |

## 2. The big picture

The system has **two phases**.

**Phase A: build time** (`chemrag build`, run once):

```
CSV ──► clean & validate ──► DuckDB  (facts: every row, cleaned, with lookup tables)
                        └──► names of chemicals / companies / brands / categories
                                   ──► gte-large embeddings ──► Chroma (vector index)
```

**Phase B: question time** (`chemrag ask "..."`, once per question), a LangGraph pipeline:

```
question
  → guard         (blocks prompt injection, caps the length)
  → planner       (what kind of question? one or several parts? in scope?)
  → extractor     (which chemicals, CAS numbers, brands, dates are mentioned?)
  → resolver      (which exact database entity does each mention mean?  ← uses Chroma)
  → [retrieval]   (if a product name was mentioned: which product IDs?)
  → [clarify]     (if ambiguous: ask "which one did you mean?")
  → query         (run pre-written, parameterised SQL  ← uses DuckDB; loops per sub-question)
  → synthesizer   (numbered facts → templated short answer + LLM-written details)
  → verifier      (do all numbers and citations match the facts? if not, fall back)
  → finalize      (answer, evidence, query plan, assumptions, warnings, confidence)
```

**Seven agents, ten graph nodes.**
- The agents are planner, extractor, resolver, retrieval, query, synthesizer and verifier.
- The support nodes are guard, clarify and finalize.
- Only **three** nodes call the LLM: planner, extractor and synthesizer.
- Every node has a non-LLM fallback.

## 4. Root files

### `README.md`
- **Contains:** setup steps (including Windows), the architecture diagram, a table of all agents, data-cleaning decisions with real numbers, evaluation results, the memory budget, design decisions and known limitations.
- **Does:** it is the front door for anyone opening the repo.
- **Why:** an interviewer usually reads the README first, so it states results honestly. That includes the held-out first run of 10/14, not only the in-sample 37/37.

### `PLAN.md`
- **Contains:** the design plan written *before* coding: data findings, data model, architecture, agent specs, retrieval design, query layer, safety policy, output contract, evaluation plan and milestones. §14 records every place the build deviated from the plan, and why.
- **Why:** it shows the work was planned, not improvised. The deviations table is useful in interviews because it shows decisions changing when measurements disagreed with assumptions, for example Qdrant → Chroma and Gemini → OpenAI.

### `Makefile`
- **Contains:** shortcuts: `make setup`, `build`, `demo`, `test`, `eval`, `eval-holdout`, `lint`, `doctor`, `graph`, `clean`.
- **Why:** "runs locally with one command" was a requirement. `make demo` creates the environment, builds the data and asks six showcase questions. Windows users run the equivalent commands from the README instead.

### `pyproject.toml`
- **Contains:** the package name (`chemrag`), the Python version (3.11+), dependencies, optional extras (`dev`, `gemini`), the `chemrag` command-line entry point, and lint/test settings.
- **Why:** this is the single source of truth for dependencies. Installing it creates the `chemrag` command.

### `requirements.txt`
- **Contains:** one line that installs the project from `pyproject.toml` with dev tools.
- **Why:** many people expect `pip install -r requirements.txt`. Pointing it at `pyproject.toml` avoids keeping two dependency lists in sync.

### `.env.example`
- **Contains:** every setting, with defaults and comments: OpenAI key and model, reasoning effort, embedding model, Chroma path, DuckDB limits.
- **Why:** you copy it to `.env` and fill in your key. The real `.env` is git-ignored, so secrets never reach GitHub.

### `.gitignore` / `.gitattributes`
- **`.gitignore`:** keeps generated or secret files out of git: the virtual environment, `.env`, `data/processed/`, `runs/` and caches.
- **`.gitattributes`:** stores the CSV byte-for-byte, with no line-ending conversion. This matters because citations rely on row positions and the build checks the file's hash.

- **Why never modified:** it is the ground truth for citations. A `row_id` is a row's position in this file.

| `chroma/` | The vector index of entity names (and optionally product names) | Lets the resolver match misspelled or synonym names |
| `index_manifest.json` | Records which embedding model, CSV hash and point counts built the index | The build can skip work when nothing changed, and detects a stale index |

## 6. `config/chemical_groups.yaml`

- **Contains:** hand-curated **synonym groups** and **families** of chemicals.
  - A **group** means the same substance under different reported names, e.g. *Retinyl palmitate = Vitamin A palmitate = Retinol palmitate*, or *Titanium dioxide* and its "airborne particles" variant.
  - A **family** means related but different substances, e.g. retinoids, talc, crystalline silica.
  - It also lists everyday synonyms: "BPA" → Bisphenol A, "oxybenzone" → Benzophenone-3, "TEA" → Triethanolamine.
- **Does:** the build reads it to assign every chemical name to a group. The resolver uses the synonyms for exact matching.
- **Why hand-curated and not an LLM or embeddings:** there are only 123 chemical names, and a wrong grouping would silently produce wrong counts. A short, reviewed file is more trustworthy. The build **fails loudly** if the file names a chemical that doesn't exist in the data.
- **Why groups and families differ:** asking about "retinol" shouldn't silently include retinyl palmitate, which is a different substance. Groups merge true synonyms. Families only produce an informational "related entries" warning, unless you explicitly ask for the family ("retinoids").

## 7. The `chemrag/` package

Each file below follows the same pattern: **Contains → Does → Why → Interview line.**

### 7.1 Foundations

#### `settings.py`
- **Contains:** one frozen `Settings` object with every configurable value: file paths, LLM provider, model, key and reasoning effort, embedding model, DuckDB memory limit, output limits, and the **resolution thresholds** (≥0.90 resolved; 0.75–0.90 resolved with an assumption; two candidates within 0.05 counts as ambiguous).
- **Does:** reads environment variables and `.env` once. Holds the budget-friendly default model per provider (`gpt-5-mini` for OpenAI).
- **Why:** there are no hard-coded magic numbers spread around the code. Changing the model or a threshold is a config change, not a code change.
- **Interview line:** "All tunable behaviour lives in one place and comes from environment variables, so the same code runs in rules-only mode, with OpenAI, or with Gemini."

#### `schemas.py`
- **Contains:** every data contract, as Pydantic models:
  - **Question understanding:** `Intent` (lookup, list, compare, summarize, trend, data_quality, coverage, out_of_scope), `SubTask`, `Plan`
  - **Extraction:** `Mention`, `DateConstraint`, `Extraction`
  - **Resolution:** `Candidate`, `Resolution`, `ProductResolution`
  - **Querying:** `ToolCall` (the exact SQL and its parameters), `ToolResult`
  - **Answer building:** `Fact`, `EvidenceItem`, `WarningItem`, `TraceEvent`, `Confidence`, `Clarification`, `Draft`, `Verification`
  - **Output contract:** `Response`
- **Why:** the brief asks for typed messages between agents. Typed contracts catch bugs early, make the JSON output self-documenting, and let LLM output be validated against a schema.
- **Interview line:** "Every hand-off between agents is a typed Pydantic object, and the final JSON response is one too."

#### `state.py`
- **Contains:** `TurnState`, the single object that travels through the LangGraph for one question. It holds the question, plan, extractions, resolutions, tool calls, results, assumptions, warnings, trace, facts, evidence, draft, verification and response. It also holds `RunOptions`: interactive or not, assume-best, page size.
- **Does:** list fields are **append-only**, so each node adds its outputs and nothing is overwritten. When the user answers a clarification, a newer resolution is *added*, and helper methods pick the latest one.
- **Why:** append-only state means the **trace is the query plan**. You can see exactly what every agent decided, in order.
- **Interview line:** "The state is append-only, so the audit trail comes for free."

### 7.2 `etl/`: Phase A, turning the CSV into a trustworthy database

No LLM is used anywhere in ingestion. It is deterministic Python so the same file always gives the same database.

#### `etl/normalize.py`
- **Contains:** text-cleaning helpers.
  - Trim and collapse whitespace.
  - Turn placeholders (`NA`, `None`, `N/A`, `-`) into empty values.
  - Build a **normalised key** that ignores case, accents and punctuation (`"L'Oréal USA"` → `loreal usa`).
  - Build a looser **company matching key** that also drops legal suffixes like Inc and LLC.
- **Why:** the same brand appears as `"Sally Hansen"` and `"Sally Hansen "`. Grouping and matching need one consistent key. These helpers are shared by the build, the resolver and the tests.

#### `etl/cas.py`
- **Contains:** CAS number handling.
  - A **check-digit validator**: CAS numbers have a built-in checksum.
  - A **normaliser** that repairs messy values: `"CAS #79-81-2"`, `"93 15 2"`, `"79812"`.
  - A "did you mean?" helper for mistyped CAS numbers.
- **Does:** labels each raw value as valid, repaired, missing, invalid, or the `"0"` used for trade secrets.
- **Why:** about 25 of the 125 distinct CAS strings in the data are dirty. A repair is accepted **only if the check digit proves it correct**, so nothing is guessed. `"50-78-25"` stays invalid rather than being reshaped into some other real CAS number.
- **Interview line:** "I used the CAS checksum as a correctness proof: a repair is only accepted when the maths confirms it."

#### `etl/build_db.py`
- **Contains:** the whole ingestion pipeline.
- **Does, in order:**
  1. Fingerprints the CSV with a SHA-256 hash.
  2. Reads every column as text and **checks the 22-column schema**, stopping if it changed.
  3. Gives every row a permanent `row_id`, its position in the file.
  4. Cleans text and placeholders.
  5. Parses dates strictly. Impossible dates, such as removals in 2103/2104, are set to empty with the raw value kept. Suspicious dates, such as discontinued before first reported, are flagged.
  6. Repairs CAS numbers with the check digit. When unrepairable, it fills from the chemical's internal ID only if that ID maps to exactly one valid CAS.
  7. Flags exact duplicates (254), "Trade Secret" rows and the test record.
  8. Assigns chemical groups from the YAML file.
  9. Builds lookup tables for products, companies, brands, categories and chemical groups, plus a single **alias table** of every known name and synonym.
  10. Logs every change in a data-quality table.
  11. Writes to a temporary file and swaps it in, so a failed build never leaves a half-written database.
- **Tables it produces:**

| Table | Holds | Why |
|---|---|---|
| `raw_rows` | The CSV exactly as received | Proof of the original values |
| `fact_report` | One cleaned row per CSV row, with flags and links to the lookup tables | The table every query runs on |
| `dim_product` | One row per product (CDPHId): name, company, brand, dates, discontinued | Product-level facts |
| `dim_chemical`, `dim_chemical_group` | Chemicals and synonym groups/families | Chemical identity |
| `dim_company`, `dim_brand`, `dim_primary_category`, `dim_subcategory` | Canonical names | Merges spelling variants |
| `entity_alias` | Every name and synonym → canonical ID | Feeds the resolver and the vector index |
| `dq_issues` | Every repair or flag, with row_id and reason | Data quality is transparent and queryable |
| `dataset_meta` | File hash, row counts, date coverage per column | Detects stale builds and powers "no data in range" answers |

- **Why this design:**
  - **Never guess.** Unprovable values become empty and flagged.
  - **Never delete.** The raw data is kept and every change is logged.
  - **Fail loudly** if the file's structure changes.
  - **Counting is defined explicitly:** a product is a distinct CDPHId, a report record is a ChemicalId, and a row is a row_id.
- **Interview line:** "Ingestion never guesses and never deletes. Every repair is logged with its row ID, so data quality is itself something you can ask about."

### 7.3 `query/`: safe, exact SQL

#### `query/filters.py`
- **Contains:** the `Filters` object, holding which chemicals, CAS numbers, companies, brands, products, categories, date ranges, discontinued/removed status and exclusions apply. It also has a compiler that turns those filters into a SQL WHERE clause.
- **Does:**
  - Every value is passed as a **bound parameter**, never pasted into the SQL text.
  - Column names come only from a fixed list.
  - Product-level conditions (category, dates, discontinued) are written so they still work when the chemical row and the category row are different rows of the same product.
  - It also produces the plain-English description of the filters ("containing Talc, discontinued in 2015") used in answers.
- **Why:** this is the SQL-safety guarantee. User text, and even LLM output, can never change the SQL structure.

#### `query/tools.py`
- **Contains:** `QueryEngine`, a **read-only** DuckDB connection with a memory cap, external access disabled and a per-query timeout. It provides a fixed set of query tools:

| Tool | Answers |
|---|---|
| `find_products` | Which products match: a list plus authoritative totals |
| `count_products` | How many, optionally grouped by company, brand, chemical or category |
| `chemicals_for` | Which chemicals are reported for X; trade secrets counted separately |
| `trend_by_year` | Products per year, with every year filled in, including zeros |
| `dataset_coverage` | What date range and how much data exists |
| `dq_summary` | Which data-quality issues were found and how they were handled |

- **Does:**
  - **Every query is logged** as a `ToolCall`: the exact SQL, the bound parameters, the row count and a fingerprint of the result.
  - Evidence rows are sampled **evenly across chemicals**, so titanium dioxide (in 87% of products) can't crowd out everything else.
  - `replay` re-runs a logged query and checks the result is identical.
- **Why:** there is **no text-to-SQL**. An LLM writing SQL is the main source of unverifiable answers. Fixed templates with typed filters cover every question type in the brief.
- **Interview line:** "The LLM never writes SQL. Six parameterised tools cover every question type, and each answer can be replayed to prove it's reproducible."

### 7.4 `retrieval/`: matching what the user typed to what's in the data

#### `retrieval/embed.py`
- **Contains:** two embedding backends.
  - **gte-large**, the default: a 1024-dimension model running on CPU via sentence-transformers. It loads lazily, its input length is capped for speed, and its thread count is limited.
  - **hash-ngram**, an offline stand-in. It is not semantic; it exists so the vector code can be tested without downloading a model.
- **Why lazy loading:** questions that resolve by exact name, synonym or CAS never load the 1.5 GB model, which matters on an 8 GB laptop.

#### `retrieval/vector_store.py`
- **Contains:** a small wrapper around **embedded Chroma** (on-disk files, no server). It can create, upsert, count, drop and search collections, and supports metadata filters such as "only products of brand X".
- **Why Chroma:** it replaced Qdrant after measurement. Embedded Qdrant held the 33k product vectors in RAM (~1.4 GB peak per question); Chroma keeps its index on disk (~0.4 GB). Because the rest of the code only talks to this small wrapper, the swap touched almost nothing else.

#### `retrieval/build_index.py`
- **Contains:** the build step that embeds names into Chroma.
- **Does:**
  - Embeds about 3.8k **entity names**: chemicals with synonyms, companies, brands, categories.
  - Optionally embeds about 33k **product names** (`--products`).
  - Works in small batches and upserts immediately, so memory stays low. The product step can resume if interrupted.
  - Records a manifest so an unchanged index is not rebuilt.
  - Measures a calibration "floor": the typical similarity of two unrelated names. gte-style models give even unrelated names fairly high scores, so this is used to rescale them.
- **Why names and not rows:** rows are structured records, and 81% of them are titanium dioxide. Vectors can't count, and embedding rows would give near-duplicate, unciteable results. Embedding cost grows with the number of *distinct names*, not rows.

#### `retrieval/resolver.py`
- **Contains:** `EntityResolver`, the "librarian".
- **Does:** for each mention it tries, in order:
  1. **CAS path:** normalise and check-digit-validate. "75070" → 75-07-0. "75-07-1" → "did you mean 75-07-0?"
  2. **Exact or alias:** match against the alias table, so "BPA" and "vitamin A palmitate" resolve instantly.
  3. **Fuzzy and vector:** a spelling score (rapidfuzz) blended with a meaning score (gte-large in Chroma, calibrated). The weighting is 65% spelling and 35% meaning, because typos are the common case.

  It then decides **resolved**, **ambiguous** (two different entities score about the same, e.g. "Pure" → Pure Ice / Pure Cosmetics / Perfectly Pure) or **not found** (with suggestions). It also resolves **product names** to product IDs, and flags generic names like "Lipstick" (28 products from 17 companies).
- **Why:** this is the "Semantic Retrieval agent" from the brief. Every decision keeps its scores and method, so the trace explains *why* a match was chosen. If vectors are unavailable, it keeps working on spelling alone.
- **Interview line:** "Vectors answer one question only: which entity did the user mean? Facts always come from SQL."

### 7.5 `llm/`: the language model, kept on a short leash

#### `llm/base.py`
- **Contains:**
  - The one-method `LLMClient` interface: "give me a structured answer matching this schema".
  - The `LLMUnavailable` error.
  - A helper that wraps user text as **untrusted data** for prompt-injection safety.
  - The simple Pydantic schemas the LLM must fill: plan, extraction and narrative bullets.
- **Why:** any provider fits behind one method. The LLM can only return validated structures, never free-form instructions.

#### `llm/openai_client.py`
- **Contains:** the OpenAI implementation. It uses structured outputs with the Pydantic schemas.
- **Does:**
  - Reasoning models (gpt-5 family) get `reasoning_effort=low`; other models get temperature 0.
  - If the API rejects a setting, it drops that setting and retries once.
  - Rate limits and timeouts are retried by the SDK.
  - **Circuit breaker:** a bad key, unknown model or no network switches the LLM off for the rest of that question, so the remaining agents don't each wait on retries.
  - Counts tokens, so each answer reports its LLM usage for cost visibility.
- **Why `gpt-5-mini`:** the LLM only classifies, extracts names and writes a few bullets. A small model is enough and costs well under a cent per question.

#### `llm/gemini_client.py`
- **Contains:** the same interface for Google Gemini, which was the original provider.
- **Why kept:** it shows the interface really is swappable, and it is a fallback option (`CHEMRAG_LLM_PROVIDER=gemini`).

#### `llm/null_client.py`
- **Contains:** `NullClient`, the "no LLM" stand-in, plus `make_llm`, which picks OpenAI, Gemini or none from the settings.
- **Why:** with no key, or with `--no-llm`, every agent automatically uses rules. The **whole evaluation set passes with no LLM**, which shows graceful degradation.

#### `llm/prompts/planner.md`, `extractor.md`, `synthesizer.md`
- **Contain:** the three system prompts.
  - The planner prompt defines scope and intent and asks for self-contained sub-questions.
  - The extractor prompt defines the entity types and says to copy text exactly, without correcting or inventing.
  - The synthesizer prompt says to use only the given facts, cite `[F#]` on every bullet, copy numbers verbatim, give no health advice, and compute no new percentages.
- **Why separate files:** prompts are reviewable like documentation and versioned with the code.

### 7.6 `agents/`: one file per graph node

#### `agents/context.py`
- **Contains:** `AgentContext`, the long-lived shared tools (settings, query engine, resolver, LLM), plus small helpers for timing and trace events.
- **Why:** heavy objects like the database connection are built once and shared, and kept out of the state that gets serialised.

#### `agents/guard.py`: the security guard
- **Does:** caps the question at 1,000 characters and removes sentences that look like prompt injection ("ignore previous instructions", "print your system prompt", SQL like `DROP TABLE`), adding a warning. If nothing answerable is left, it refuses.
- **Why:** this is the first of several injection defences. The others are that user text is wrapped as data, LLM output must match a schema, the LLM has no tool authority, the database is read-only, and the verifier checks the output.

#### `agents/planner.py`: the manager (brief role 1: Orchestrator/Planner)
- **Does:**
  - Decides **scope**: in scope, medical advice (politely refused, but still gives the factual part), or unrelated.
  - Classifies **intent** for each part.
  - **Splits multi-part questions** into up to four sub-questions.
  - Uses the LLM when available and keyword rules otherwise.
  - A deterministic medical-advice check runs even if the LLM missed it.
- **Why:** the LLM classifies, but it doesn't choose which tools run. Routing stays deterministic.

#### `agents/extractor.py`: the note-taker (brief role 2: Entity & Constraint Extraction)
- **Does:** finds the details of each sub-question, in layers.
  1. **Patterns:** CAS numbers, years and ranges ("between 2015 and 2018", "since 2016", "last 3 years"), discontinued/removed wording, "top 5", "by company", "excluding X".
  2. **Exact name scan:** matches against all known names ("Sally Hansen", "Nail Products").
  3. **Cue phrases:** "contains X", "brand X", quoted product names, category words like "shampoos". These catch misspellings for the resolver to fuzzy-match.
  4. **LLM:** may add mentions, but only text it quotes from the question.
  - It decides **which date field** a year refers to (first reported, most recent, discontinued, removed) and records an assumption when it uses the default.
  - A follow-up like "…and how many were discontinued?" **inherits** the previous sub-question's entities.
- **Why rules first:** they are fast, free and predictable. The LLM only adds to them, so it can't invent entities.

#### `agents/resolution.py`: three nodes (resolver, retrieval, clarify)
- **Resolver node (brief role 4):** runs the resolver on each mention.
  - In assume-best mode, an ambiguous match becomes the top choice plus a warning.
  - A low-confidence cue phrase that matches nothing is ignored, with a note, rather than blocking the answer.
- **Retrieval node:** resolves product-name mentions to product IDs, narrowed by any brand or company also mentioned.
- **Clarify node:**
  - Builds "Which brand did you mean by 'Pure'?" with options and product counts.
  - In the interactive CLI it **pauses the graph** (LangGraph `interrupt()`), waits for your choice, then continues.
  - In JSON mode it returns a clarification response instead.
- **Why:** the brief requires ambiguity handling. Guessing silently would produce confidently wrong answers.

#### `agents/query_agent.py`: the accountant (brief role 3: Structured Query)
- **Does:**
  - Turns resolved entities and constraints into a `Filters` object, then picks the tool by intent: list → `find_products`, how many → `count_products`, chemicals → `chemicals_for`, trend → `trend_by_year`. Compare and summarize use several tools together.
  - **Before querying:** if a date range is entirely outside the data, it answers "no data in range" with the real coverage instead of running a query. Partial overlaps are clipped, with a warning.
  - **Unresolved entity:** it does not run a query with that constraint silently dropped. It reports "not found" with suggestions.
  - **Empty result:** it re-runs the count with one constraint dropped at a time and explains which one emptied the result ("without the category filter there would be 1 product").
  - **Warnings:** one chemical dominates the result, a brand belongs to several companies, synonyms were merged, related chemicals exist, a CAS number was repaired, trade-secret chemicals are present, or the list was truncated.
  - **Assumptions:** "contains" includes chemicals later removed, and trend years refer to the first-reported date.
  - Loops once per sub-question.
- **Why:** this is where correctness and honesty live. All the "graceful handling" requirements in the brief are implemented here, with real database checks.

#### `agents/synthesizer.py`: the writer (brief role 5: Answer Synthesizer)
- **Does:**
  - Converts query results into **numbered facts** (F1…Fn).
  - The **short answer is filled from a template**, so it can't contain an invented number.
  - **Details** are a deterministic listing (products, chemicals, year bars, comparisons), optionally preceded by **LLM bullets that must cite `[F#]`**.
  - Picks **evidence rows** round-robin across results and attaches the fields used.
  - Handles medical refusals: it states that the dataset doesn't assess safety, gives the factual count, and links to CDPH.
- **Why:** it separates *what is true* (facts) from *how it is phrased* (the LLM).

#### `agents/verifier.py`: the fact-checker (guardrail, beyond the brief)
- **Does:** checks the draft.
  - Every number must appear in the facts or query results.
  - Every LLM bullet must cite a fact that exists.
  - No invented percentages.
  - No health advice ("safe to use", "you should avoid").
  - No echo of the system prompt.
  - Evidence must be present.

  If the LLM text fails any check, it is **thrown away** and replaced with the templated details, plus a `verifier_fallback` warning.
- **Why:** LLMs can hallucinate numbers. Checking after generation is the only way to guarantee "no fabricated numbers". A test proves it: a fake LLM says "31 products", and the system still answers 30.

#### `agents/finalize.py`: the receipt
- **Does:** assembles the `Response`: answer, details, evidence, facts, query plan (the numbered trace), clarification, assumptions, de-duplicated warnings, confidence and metadata (LLM used, model, vectors on/off, timing).
- **How confidence is computed:** start from the lowest of the intent confidence and the entity match scores, then multiply by a documented penalty for each warning type (e.g. ambiguous ×0.7, not found ×0.6, verifier fallback ×0.85). Then bucket it as high, medium or low.
- **Why a formula:** it is explainable. You can say exactly why an answer is "medium".

### 7.7 Wiring and entry points

#### `graph.py`: the LangGraph
- **Contains:**
  - The **ten nodes**.
  - The **edges**.
  - The **router functions**: small, pure Python that decides "after the resolver: clarify, product retrieval, or straight to SQL?", "after the query: next sub-question or synthesise?" and "refuse or continue?".
  - Compilation with a checkpointer, needed for pause/resume, restricted to this project's own data types.
- **Why LangGraph:**
  - The workflow is a real graph with branches (clarify, refuse, hybrid) and a loop (multi-part questions).
  - LangGraph's `interrupt()` provides genuine human-in-the-loop clarification.
  - `chemrag graph` exports the diagram from the running code, so the docs can't drift from reality.
- **Why routers aren't LLM-driven:** predictable and unit-tested. The LLM never decides what runs next.

#### `orchestrator.py`: the front desk
- **Does:**
  - Builds everything once: database engine, resolver, LLM client, graph.
  - Runs a question through the graph, handling the pause/resume loop for clarifications.
  - Adds per-question LLM token usage to the response.
  - **Saves a run file** (`runs/<id>.json`) with the response and every SQL call.
  - Provides `replay`, which re-executes the logged SQL with no LLM and confirms identical results.
- **Why:** this is the single entry point used by the CLI, the tests and the evaluations, so all three exercise the same code path.

#### `cli.py`: the `chemrag` command

| Command | What it does |
|---|---|
| `chemrag build [--products] [--force] [--skip-index]` | ETL in a separate process (so its memory is released), then the vector index |
| `chemrag ask "…" [--json] [--no-llm] [--no-vectors] [--assume-best] [--limit] [--page]` | Ask a question; pretty output or raw JSON |
| `chemrag replay <id>` | Re-run a past answer's SQL and verify the results are identical |
| `chemrag eval [--holdout] [--no-llm]` | Run an evaluation set and write a report |
| `chemrag doctor` | Check RAM, database, index, embedding model, LLM key and model, and make one test LLM call |
| `chemrag graph` | Regenerate `docs/graph.md` from the compiled graph |

#### `render/cli_render.py`
- **Does:** draws the terminal output with Rich:
  - an answer panel with response type and confidence,
  - a details panel,
  - an evidence table (row_id, CDPHId, CSFId, ChemicalId, product, company/brand, chemical/CAS, dates),
  - the query plan (each agent step plus each SQL statement and its parameters),
  - assumptions and warnings,
  - a footer with the request ID for replay.
- **Why:** the brief asks for an answer, evidence, query plan and warnings. This shows all four on one screen for a demo.

#### `__init__.py` files
- Mark folders as Python packages. They contain no logic.

## 8. `evals/`: proving it works

#### `evals/golden.yaml`
- **Contains:** **37 test questions**, each with the expected response type, intents, canonical entities and required warnings.
- **Coverage:**
  - Every intent.
  - Misspellings, CAS-only and bare-digit CAS, and an invalid check digit.
  - Synonyms and families.
  - Out-of-range and invalid dates.
  - An ambiguous brand and a generic product name.
  - Multi-part and follow-up questions, trends, comparisons, top-N.
  - Empty results, data quality, coverage.
  - Medical refusal, out-of-scope, prompt injection, missing entity.

#### `evals/holdout.yaml`
- **Contains:** 14 **paraphrased** questions written *after* the system was built, to test generalisation honestly.
- **Why it matters:** the first untouched run passed **10/14**. That number is reported, and the failures led to general fixes. It shows the 37/37 golden score is optimistic, and that I measured generalisation rather than only in-sample accuracy.

#### `evals/ground_truth.py`
- **Contains:** hand-written pandas calculations over the **raw CSV**, one per question, plus a check that each cited row really supports the answer.
- **Why independent:** it shares **no code** with the system (not the cleaning, resolver or SQL). If the system has a bug, the two disagree instead of agreeing on the same mistake.

#### `evals/run_eval.py`
- **Does:** runs every question and scores it:
  - response-type accuracy,
  - intent accuracy,
  - entity-resolution accuracy,
  - **answer correctness** (exact counts, chemical sets, trends, top-N, comparisons),
  - **citation precision** (every cited row re-checked against the raw CSV),
  - warning recall,
  - refusal/clarification accuracy.

  It writes Markdown and JSON reports.

#### `evals/results/`
- **Contains:**
  - the golden report (37/37 in rules-only mode),
  - the held-out report,
  - **`holdout_first_run_untuned.md`**, the honest first run (10/14).
- **Why committed:** reviewers can see the results without running anything.

## 12. "Why did you…?": design Q&A

| Question | Answer |
|---|---|
| Why not embed all 114k rows and do classic RAG? | Rows are structured, and 81% are one chemical. Vectors can't count, and near-duplicate rows make citations meaningless. SQL gives exact, citable answers, so vectors are used only to match names. |
| Why is the LLM not allowed to write SQL? | It is the main source of unverifiable answers and an injection risk. Six fixed, parameterised tools cover every question type in the brief. |
| Why DuckDB over SQLite or Postgres? | It is embedded with no server, fast at group-bys and trends, reads CSV natively and handles dates well. It can be opened read-only and memory-capped. |
| Why Chroma over Qdrant? | Measured: embedded Qdrant held vectors in RAM (1.43 GB peak on a product question) while Chroma used 0.41 GB. The 8 GB laptop and no-server requirements decided it. |
| Why LangGraph if routing is deterministic? | The workflow has branches, a loop and a pause for clarification. LangGraph provides those, a typed state and a diagram generated from code, while the routing logic stays plain, testable Python. No LangChain agents or wrappers are used. |
| Why rules first, LLM second? | It is predictable, free and testable, and the system works with no LLM (the eval passes). The LLM adds paraphrase coverage and nicer wording, and the verifier keeps it grounded. |
| How do you prevent hallucinated numbers? | The short answer is templated from facts, LLM bullets must cite facts, and the verifier rejects any number not in the results. A test injects "31" and the system still answers 30. |
| How do you handle ambiguity? | Exact match, then fuzzy and vector match. If two different entities are within 0.05 of each other, it asks. In the interactive CLI the graph pauses and resumes after your choice. |
| What if the data is bigger? | Ingestion would move into DuckDB SQL (streaming, out-of-core), clean *distinct values* instead of rows, and load incrementally. Embedding cost barely grows because only names are embedded. |
| How do you know it's right? | Independent pandas ground truth over the raw CSV, citation re-checking, 94 tests, and an honest held-out first run of 10/14. |
| Why gpt-5-mini? | The LLM only classifies, extracts and phrases, so a small model is enough at well under a cent per question. Per-answer token usage is reported. |

## 14. Known limitations and next steps

**Limitations**
- The rules-only extractor relies on patterns, so unusual phrasing needs the LLM. The held-out set shows this.
- Dates are handled at year level ("June 2019" becomes 2019).
- Comparison works across one dimension at a time.
- Embedding product names is optional because it takes 10–25 minutes on CPU.
- Ingestion is pandas in memory, which is fine up to about a million rows.

**Next steps**
- Run the evaluation with the LLM on and report rules-only vs LLM.
- Move ingestion into DuckDB SQL with incremental loads.
- Add month-level dates.
- Collect real user questions as a new held-out set.
- Add an optional small API or UI if servers become acceptable.

## 15. Glossary

| Term | Meaning |
|---|---|
| **CDPHId** | ID of a product |
| **CSFId** | ID of a shade or variant of a product (often empty) |
| **ChemicalId** | ID of one product–chemical *report*. Despite the name, it is not a chemical |
| **CAS number** | The international chemical registry number, with a built-in check digit |
| **row_id** | A row's position in the CSV; what citations point to |
| **Chemical group / family** | Same substance under different names / related but distinct substances |
| **Alias** | Any name or synonym that maps to a canonical entity |
| **Resolution** | Turning a user's words into exact database IDs |
| **Embedding / vector** | A list of numbers representing a text's meaning; similar texts get similar vectors |
| **Fact sheet (F1…Fn)** | Numbered facts from query results; the only numbers an answer may use |
| **Verifier fallback** | Replacing LLM text with templated text when it fails the checks |
| **Circuit breaker** | Switching the LLM off for the rest of a question after a hard failure |
| **Replay** | Re-running an answer's logged SQL to prove the result is identical |
| **Golden / held-out set** | Test questions used during development / written afterwards to measure generalisation honestly |
